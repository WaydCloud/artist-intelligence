# 2026-07-30 · 모션 — 두 곳을 더하고, 기각 목록과 reduced-motion 안전망을 남겼다

> 세션 스냅샷(이력). 다음 행선지는 [`../HANDOFF.md`](../HANDOFF.md), 결정 이유는 [`../docs/DECISIONS.md`](../docs/DECISIONS.md) D-046.
> 이전 스냅샷: [`2026-07-30-interaction-crosshair-tooltip.md`](2026-07-30-interaction-crosshair-tooltip.md).

## 1. 한 줄 요약

**모션에서 부족했던 것은 사용처가 아니라 규율이었다. 쓰는 곳을 넷으로 한정하고 쓰지 않는 곳을 이유와 함께 적었으며(§7.7), `prefers-reduced-motion`을 한 곳에서 집행하게 했다. 그리고 이번에도 결함 하나가 내가 방금 쓴 코드에서 나왔다 — 게이트 넷과 정지 스크린샷을 전부 통과한 채로.**

## 2. 화면을 훑고 나서 바뀐 판단

재개점은 "모션을 추가한다"였는데, 실제로 훑어보니 **더 쓸 곳보다 규율이 없다는 것이 문제**였다. `DESIGN.md` §5에 상한(시간·반복·reduced-motion)이 있고 §7에 과용 경고가 있는데, **어디에 쓰지 않는지**가 없었다. 그래서 이번 산출물의 절반은 기각 목록이다.

기준은 하나다: **이 움직임이 없으면 읽는 사람이 무엇을 놓치는가.** 답이 "없음"이면 장식이다.

## 3. 더한 것 둘

| 어디 | 무엇을 설명하나 | 어떻게 |
|---|---|---|
| 튜너 막대 (`Tunable.BucketRows`) | 임계를 움직였더니 **얼마나 옮겨갔나** | 폭 전환 150ms ease-out (CSS). 곡 수 숫자는 즉시 — 정확한 값이 늦게 도착할 이유가 없다 |

기존 두 곳(추론 펼침 · 구획 전환)은 그대로 두었다.

## 4. 🔴 새로 쓴 코드에서 나온 결함 — 행 재정렬

튜너의 칸은 곡 수로 정렬돼 있어 임계를 움직이면 순서가 자주 뒤집힌다. 5번째 칸이 2번째로 뛰어오르면 눈이 그 칸을 놓치므로 `layout="position"`(motion)을 걸었다.

**결과: 22px짜리 행 셋이 서로를 통과하면서 이름과 숫자가 포개져 읽을 수 없는 더미가 됐다** — 스크린샷에서 `33`과 `14`가 한 줄에 겹쳐 있었다. 증거 위에 오버레이를 얹지 않는다는 §4를 움직임이 **시간축에서** 위반한 것이다.

그리고 더 나쁜 두 번째 사실: **슬라이더는 연속 입력이다.** 드래그는 초당 수십 번 상태를 바꾸므로 위치 전환은 끝나지 않는다 — 드래그하는 내내 중간 상태만 보인다. 크로스헤어에 전환을 넣지 않기로 한 것과 같은 이유다. 되돌리고 폭 전환만 남겼다.

**어떻게 잡았나** (순서가 곧 교훈이다):

1. `lint` · `tsc` · `validate_report_data`(CLEAN + selftest 81/81) · `smoke:tabs`(12/12 PASS) — 전부 통과.
2. **정지 스크린샷도 멀쩡했다.** 애니메이션이 끝난 뒤 상태는 정확했다.
3. 화살표 키 여섯 번 → **중간 프레임**을 캡처해서야 겹침이 보였다.
4. 그것이 드래그에서는 상시 상태라는 것은 **마우스로 실제 드래그해 보고** 알았다(키 입력은 이산이라 재현되지 않는다).

> 모션 결함은 렌더 육안보다 한 겹 더 안쪽이다. 인터랙션 결함이 스크린샷으로 안 보였던 것(D-045)의 **다음 층**이고, 이번엔 정지 프레임으로도 안 보였다.

## 5. reduced-motion — 규칙은 있었는데 집행이 없었다

§5는 "`prefers-reduced-motion` 존중"을 요구한다. 실제로는 `motion/react`를 쓰는 두 컴포넌트만 `useReducedMotion`으로 접고 있었고 **CSS 전환 23곳은 전부 무시**하고 있었다. 전환이 컴포넌트마다 흩어져 있어 **하나만 빠뜨려도 눈으로 셀 수 없다** — §7.3~§7.6의 결함들과 같은 부류다.

`globals.css`에 전역 규칙 하나를 두어 **시간만 0으로** 만들었다(상태 변화는 그대로 일어난다). `0.01ms`는 0이 아니라서 `transitionend`에 매인 코드가 있어도 깨지지 않는다.

CSS 밖의 예외 둘은 호출부에서 각자 묻는다:

- `motion/react`의 JS 애니메이션 — CSS 전환이 아니다.
- `scrollIntoView({behavior: "smooth"})` — **명시한 값이 CSS `scroll-behavior`를 이긴다.** 이 화면에서 가장 큰 모션이라 그냥 두면 안전망이 무의미했다.

## 6. 기각 목록 (이유와 함께 §7.7에)

| 기각 | 이유 |
|---|---|
| 모듈 탭 전환 | 제목까지 포함해 화면 전체가 바뀌므로 무엇이 갈렸는지 이미 명백하다. 구획 전환과 달리 설명할 것이 없다 |
| 행 재정렬 | 겹치면 못 읽는다(위 §4). 순서가 자주 뒤집히는 것은 **정렬 규칙**으로 풀 문제다 |
| 연속 입력이 만드는 위치 변화 | 끝나지 않는다. 겹쳐도 읽히는 값(폭·불투명도)만 전환에 싣는다 |
| 테마 전환 · 지표 타일 · 숫자 카운트 | 정확한 값이 늦게 도착할 이유가 없다 |
| `<details>` 펼침(정의·표 뷰) | 네이티브 요소를 상태 위젯으로 바꾸는 것은 §7.6에서 배운 것과 반대 방향 |
| 크로스헤어 · 툴팁 | 즉시성이 곧 정확성 |

## 7. 게이트로 옮기지 않았다 (조건은 적어 뒀다)

인터랙션은 요구를 `smoke:tabs`로 옮겼지만(D-045) 모션은 옮기지 않았다 — **사용처가 3곳뿐**이라 문서와 리뷰로 충분하고, 게이트 자체의 유지비가 더 크다. 대신 조건을 미리 적었다: **5곳을 넘으면 옮긴다.** "언젠가"가 되지 않게 하기 위한 것이다.

검사는 임시 스크립트로 했다(커밋하지 않음): 노브를 돌린 뒤 잔여 `transform` 없음 · reduced-motion에서 40ms에 이미 최종 상태 · **드래그 20스텝 동안 행 겹침 0쌍** · 막대가 최종 값에 도달(오차 0.00%) · 라이트/다크 각각.

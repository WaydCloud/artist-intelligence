## 2. 🔴 먼저 풀어야 하는 것 — 코드보다 결정이 앞선다

### 2.1 아키텍처 불변식이 정면으로 걸린다

`AGENTS.md` §3은 **"임의로 라이브 백엔드·서버·인증·DB 추가 금지"**다. SaaS는 그 셋을 전부 요구한다. 이건 규칙 위반이 아니라 **규칙을 바꿀 결정**이며, 근거를 새 결정으로 남기면 된다(D-003이 이미 "라이브 분석이 필요해지면 Python 비동기 워커(Modal 1순위)"로 길을 열어 두었다).

> ✅ **미결이던 논의가 이 지시로 풀린다.** `HANDOFF.md`의 🟡 "상시 서버"는 **서버가 정당해지는 조건 3개**를 적어 두고 "아직 셋 다 아니다"라고 했다: ① 여러 사람이 쓴다 ② 온디맨드 분석이 필요하다 ③ JSON-in-git이 규모를 넘는다. **SaaS는 셋을 동시에 참으로 만든다.** 그러므로 이 전환의 첫 결정은 "서버를 둘 것인가"가 아니라 **"어떤 서버를, 무엇까지"**다.

### 2.2 🔴 수집이 이 PC 한 대에 묶여 있다 (가장 실질적인 병목)

지금 모든 관측은 **Windows Task Scheduler + 이 PC**에서 나온다. SaaS는 그 위에 세울 수 없다.

- **`data/live/`는 gitignore다.** 관측 이력이 git 밖에 있고 **이 PC에만** 있다(65MB). 고객에게 파는 시계열의 원본이 백업 없는 로컬 디스크에 있다는 뜻이다.
- **멜론 MCP 레그는 대화형 인증이라 헤드리스 불가.** 서버 이전 시 이 렌즈는 자동으로 따라오지 않는다.
- 후보: GitHub Actions cron(서버·DB 없이 PC 의존 소멸, git이 곧 이력) → Modal 워커(D-003) → 상시 서버. **①이 실제 통증이므로 여기서 시작한다.**

### 2.3 🔴 스크롤리텔링과 책임소재 불변식의 긴장 — 이 전환의 핵심 설계 질문

`DOMAIN.md` §0: **판단은 책임질 인간에게, 도구는 증거에서 종료한다.** 그런데 **스크롤리텔링은 본질적으로 서사 형식**이다. 읽는 사람을 정해진 순서로 끌고 가 결론에 도착시키는 것이 그 장르의 힘이고, 그것을 그대로 쓰면 **도구가 평결을 배달하는 형태**가 된다 — 불변식이 정확히 금지하는 자리다.

**그러나 기각할 이유는 아니다.** 두 가지를 가르면 된다:

| 형태 | 예 | 판정 |
|---|---|---|
| ❌ **결론으로 데려가는 서사** | "스크롤하면 왜 이 팀이 뜰지 알게 됩니다" | 평결 배달. 금지 |
| ✅ **증거를 순서 지어 보이는 서사** | "이 축에서 이 팀이 어디 있는지, 무엇과 비교했는지, 무엇을 못 봤는지 차례로" | 불변식과 양립. **오히려 더 잘 지킨다** |

- 지금 대시보드는 **구획으로 질문을 가른다**(D-043). 스크롤리텔링은 그 질문들에 **순서**를 주는 것이고, 순서는 이미 정해져 있다(sonic-profile: 무엇인가 → 움직이나 → 진짜인가 → 우리 팀은 어디). **즉 자산이 이미 그 형태에 가깝다.**
- 🔴 **강제 스크롤·납치 스크롤 금지**는 접근성(§6)과 불변식 양쪽에서 온다. 읽는 사람이 **아무 때나 빠져나와 원본 수치로 갈 수 있어야** 한다.
- 🔴 **한계·불확실성이 서사에서 빠지면 안 된다.** 지금은 `reliability`·`notAnswered`가 1급 요소다. 스크롤리텔링에서 그것이 "마지막 슬라이드 각주"가 되는 순간 §5 과대주장 금지를 어긴다.

### 2.4 상업화가 새로 여는 위험 (지금까지 없던 것)

- 🔴 **저작권**: 한국 저작권법에 **TDM 면책이 없다**. 지금은 프리뷰 무보관·파생 분석만이라 회색이지만, **유료 제품**이 되면 그 회색의 성격이 달라진다. 법률 검토가 출시 전제다.
- 🔴 **태그 정확도가 영구 미측정**이다(D-054). 장르·악기 태그를 화면 중심에 두고 파는데 정확도를 재지 않기로 했다. 지금은 `참고(정확도 미측정)` 병기로 정직하지만, **유료 고객에게 그 병기가 어떻게 읽힐지는 별개 문제**다.
- **PII 게이트**는 이미 있다(수집 즉시 REJECT → quarantine). 고객 데이터·계정이 생기면 **범위가 넓어진다**(우리 고객의 개인정보).
- **가격·과금·다중 테넌시**는 도메인 소유자 결정이며 엔지니어가 정할 값이 아니다.

### 2.5 데이터 깊이가 아직 제품이 아니다

| 레일 | 깊이 | 실험 종료(2026-08-19) 기준 |
|---|---|---|
| chart | **15일** (51시장) | ~34일 |
| social | 95파일 (2026-07-19~) | 유료 · 일 $3 상한 |
| yt | 8일 | ~27일 |
| sonic | **4일** | ~23일 |

프리미엄 SaaS의 화면은 **추세**를 말해야 하는데 sonic은 4일이다. **수집을 서버로 옮기는 것이 곧 제품 깊이를 버는 일**이라 §2.2가 1순위인 이유가 여기서도 나온다.

## 4. 제안하는 순서 (엔지니어 의견 · 승인 대상)

> 원칙: **핵심 흐름을 깨지 않고 한 층씩 올린다.** 지금 프런트를 먼저 갈아엎으면 데이터가 얕은 채로 화려한 껍데기가 되고, 수집이 PC에 묶인 문제는 그대로 남는다.

1. **수집 이전**(§2.2) — GitHub Actions cron으로 옮기고 `data/live/`를 git 안으로. **PC 의존이 사라지고 이력이 백업된다.** 프런트 작업과 병행 가능하며, 그동안 데이터 깊이가 계속 는다.
2. **읽기 전용 SaaS 껍데기** — 인증 + 조직 단위 접근. 분석은 여전히 배치. **서버가 정당해지는 조건 ①만 먼저 충족**시키고 ②는 미룬다.
3. **프리미엄 프런트 v1** — 스크롤리텔링을 **한 탭에서만** 파일럿한다(D-041이 시각화를 한 탭에서 파일럿했던 것과 같은 순서). 6탭 확산은 그다음이다.
4. **온디맨드 분석** — 여기서 처음으로 Modal 워커가 정당해진다(D-003).
5. **과금·다중 테넌시** — 1~4가 서기 전에는 붙이지 않는다.

**🔴 각 단계에서 지켜야 하는 것**: `모듈 CLI → 스키마 유효 report.json` 계약 · R1~R8 · PII 게이트 · 기준 원장 노출 · 책임소재 불변식. **이것들이 프리미엄의 내용이지 장애물이 아니다** — 반박 가능한 도구는 흔하지 않다.

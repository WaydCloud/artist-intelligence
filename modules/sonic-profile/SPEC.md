# sonic-profile · SPEC (무엇을 · 누구를 위해)

> 곡의 **소리 특성**을 5번째 축으로 관측한다. 차트(무엇이 올랐나)·소셜(누가 반응하나)·YT(공식 채널)에 이어, **"어떤 소리가 그 자리에 있었나"**.
> 결정 근거: [`../../docs/DECISIONS.md`](../../docs/DECISIONS.md) D-019. 기준 정의: [`RULES.md`](RULES.md). 검증: [`TESTS.md`](TESTS.md).

## 1. 질문

이 모듈이 답하려는 것은 **하나**다.

> **워치리스트/차트 진입 곡들의 소리가 시간에 따라 어느 방향으로 움직이는가?**

답하지 **않는** 것: 이 곡이 뜰지, 이 곡이 좋은지, 이 곡이 춤추기 좋은지. 그건 결정 레이어이고 책임질 인간의 몫이다([`../../DOMAIN.md`](../../DOMAIN.md) §0).

## 2. 1차 사용자

[`../../PRODUCT.md`](../../PRODUCT.md)의 A&R·기획자. 구체적으로 이런 질문에 증거를 대는 용도다.

- "요즘 차트 상위권 BPM 대역이 내려갔나?" → tempo 분포의 시계열
- "우리 데모가 지금 차트의 저역 무게감과 얼마나 떨어져 있나?" → low_end_ratio 분포 대비 위치
- "신인 코호트의 소리가 기성과 다른가?" → 코호트별 분포 비교

**단일 곡 평결이 아니라 분포 안에서의 위치**가 산출물이다. 이건 취향이 아니라 §4의 물리적 한계에서 나오는 제약이다(30초 발췌·비결정 구간).

## 3. 핵심 흐름 안에서의 위치

```
sonic-profile fetch   (라이브)  →  프리뷰 URL 해석 · 메모리 처리 · 수치만 반환
sonic-profile signals (오프라인) →  data/live/sonic_series.json   → signal-bridge 합류
sonic-profile analyze (오프라인) →  output/report.json            → 대시보드 5번째 탭
```

[`../../ARCHITECTURE.md`](../../ARCHITECTURE.md)의 불변식(`모듈 CLI → 스키마 유효 report.json → 대시보드`)을 그대로 따른다. 기존 모듈과 동일하게 **수집(라이브) / 분석(오프라인·결정적)** 을 분리하며, 스모크는 네트워크를 타지 않는다.

## 4. 소스 · 무보관 규약

- **소스**: Apple iTunes Search API `previewUrl`(공개·무인증, 약 30초 m4a). 폴백 Deezer `preview`.
- **워치리스트 커버리지 실측**(2026-07-28): CORTIS·RESCENE·KiiiKiii·MEOVV·KEYVEATZ·Hearts2Hearts **6/6 조회 성공, 프리뷰 전건 존재**. 데뷔 직후 팀도 포함.
- **무보관**(D-019 ②): 오디오는 **디스크에 남기지 않는다**. 임시 파일을 쓰는 경우 같은 프로세스에서 반드시 삭제하고, 산출물은 **수치와 provenance뿐**이다. 이는 저장 비용 문제이기 이전에 [`../../AGENTS.md`](../../AGENTS.md) §5("파생 분석만")의 설계적 구현이다.
- **YouTube 미사용**: ToS가 다운로드를 명시 금지한다. yt-pulse가 쓰는 YouTube Data API는 메타데이터만 제공하며 오디오 표면이 없다 — 오디오를 얻으려면 ToS를 우회해야 하므로 이 축에서는 경로가 아니다.

## 5. 산출 (report.json)

- `moduleId = "sonic-profile"`, 공유 스키마([`../../packages/report-schema/report.schema.json`](../../packages/report-schema/report.schema.json)) 준수.
- **metrics**: 관측 곡 수 · 해석 실패 수 · tempo 중앙값 · pulse clarity 중앙값 · 저역 비율 중앙값 · **정박(four-on-floor) 곡 비율** 등.
- **charts** (§1의 질문에 하나씩 대응 — 단면 순위만으로는 트렌드가 보이지 않는다):
  - **분포 위치**(heatmap) — 워치리스트 트랙이 차트 코호트에서 축별 **몇 위**인가. SPEC §2의 "분포 안에서의 위치"가 이것이다.
  - **분포 추이**(line) — 축별 중앙값의 날짜 시계열. **트렌드는 분포가 움직이는가로만 보인다.** 날짜가 쌓이며 채워진다.
  - **코호트 비교**(bar) — 워치리스트 중앙값 vs 차트 중앙값(0~1 축).
  - **리듬 패턴 구성**(bar) — 코호트에서 각 킥 패턴(정박·3+3+2·싱코페이션 등)이 최고 정합인 곡 수. "지금 차트의 리듬이 무엇으로 이뤄져 있나".
  - 템포 분포(bar) · 펄스 명료도 상위(bar, `아티스트 - 곡명`).
- **insights**: 표본 수·커버리지와 함께 §4·RULES §5의 한계를 **반드시** 병기.

## 5.1 모듈 경계 (중복 방지 — [`../../AGENTS.md`](../../AGENTS.md) §1)

[`../dance-dynamics/`](../dance-dynamics/)도 librosa를 쓴다(RULES §3: `onset_strength`·`rms`). 둘은 목적이 다르므로 경계를 못 박는다.

| | sonic-profile | dance-dynamics |
|---|---|---|
| 관측 대상 | **곡의 소리** 자체 | **움직임 × 음악의 정합** |
| 질문 | 소리가 어느 방향으로 움직이는가 | 이 안무가 음악에 얼마나 붙어 있는가 |
| 음악 사용 | 지표의 본체 | 움직임을 재는 **기준선** |

- **온셋 추출은 공유 프리미티브**다. 두 모듈이 각자 구현하지 말고, 필요해지는 시점에 공통 유틸로 올린다(먼저 만드는 쪽이 `packages/`에 두고 다른 쪽이 참조).
- **`다이내믹 레인지`는 dance-dynamics가 선점한 이름**(움직임 에너지의 백분위 스프레드). 이 모듈의 압축 지표는 `crest_factor_db`로 다르게 부른다(RULES §3).

## 6. 범위 밖 (명시적으로 안 한다)

- **곡 구조 분석**(인트로/벌스/훅 경계, 드롭 타이밍, 인트로 길이) — 30초 발췌로는 측정 불가. 전곡 라이선스가 생기기 전까지 열지 않는다.
- **Spotify audio features 재현** — 정의도 학습 데이터도 다르다. 값 등치는 RULES §5에서 금지.
- **에어밴드·초고역 지표**(`spectral_rolloff` 등) — `sr=22050`이라 나이퀴스트가 11kHz다. **원리적으로 볼 수 없다.** sr을 올리면 과거 값 전부와 단절되므로(RULES §2) 열지 않는다.
